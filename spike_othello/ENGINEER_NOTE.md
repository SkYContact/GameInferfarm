# 交接说明：小模型演化支持需求（工程师向，2026-09-22）

> 背景：黑白棋 BC→演化/PG 实验要上农场全量重做。单模型推理已验证
> （fb128 = 28,813 局/s / 87 万决策/s，见 REPORT.md）；**演化负载卡在
> "一个进程一个模型"上**。本文把需求的负载形状、瓶颈量级、验收门槛写死。

## 一、要支持的两种负载

### 负载 A：ES 种群（最急）
- 每代 **P=128 个不同权重向量**（同一架构：MLP 128→128→128→64，flat 41,280 参数，
  权重就在一个 [P, 41280] 矩阵里），每个体打 8 局 vs 锚点池 → 每代 1024 局
- 每局 ~30 次串行决策（我方）+ 对手 ~30 次（锚点=历史快照，也是模型）
- **代频**：torch 参考实现 1.07s/代（B=1024 单次批量前向算全部个体：pool[P,d] +
  逐行权重索引 gather，一次 bmm 出 [P,B,64] logits）——这是要追平/超越的数
- 现状农场做不到的根因：银行一模型；逐个体 refit 的话每相位只有 8 局在飞，
  30×~2ms 延迟地板 → 每代 8-60s，比 torch 慢一个量级（在飞容量 ÷ 串行链长的结构冲突）

### 负载 B：PG 热换心（次急）
- 策略每 ~1024 局更新一次权重，需要**毫秒级**把新权重喂进正在跑的引擎继续跑
- 现状：ORT 后端无 refit API；TRT refit 存在但未接入本例
- 附带收益：锚点池协议（对手=历史快照）需要**两个模型同时在飞**（当前策略 + 锚点）

## 二、候选设计（量级供参考）

1. **逐行权重路由（最优形态）**：模型小到 41k 参数，"gather 每行权重 + 分组 matmul"
   一个 kernel 可算 P×B 行——torch 侧 forward_pop 就是这个形态（spike 里
   export/parity 脚本同款布局）。适配器侧只需在组装行时带一个 model_id。
   演化/评估/多锚点全通吃；
2. **每银行/每组多引擎 + 槽级路由**：N 个小 engine 共享调度，slot 标 model_id——
   中间形态，工程量小但吞吐受 engine 数限制；
3. **多进程一模型**（用户提议的起点）：可行但 12GB 卡上 CUDA context 每个吃
   ~200-300MB，6-12 进程是上限，128 个体装不下；适合作过渡验证。
4. **TRT refit 热换**（负载 B 单独解）：对 PG 单模型场景已够用。

## 三、验收门槛（黑盒，不依赖实现）

1. **正确性**：spike_othello/parity_check.py 三层门——规则属性测试（38,400 组零分歧）、
   ONNX vs torch 逐位、全协议对拍（与 Python 参考逐局一致，CUDA/CPU 末位差允许）。
   多模型路径建议加一条：**逐行路由的输出必须与逐模型单独跑逐位同**（我方 torch
   forward_pop/forward_gather 一致性可当参考实现）；
2. **性能**：负载 A 以"代"计——1024 局（128 个体×8）+ 权重刷新 ≤1s 即追平 torch；
   <0.3s（rollout 0.1s 内 + 路由开销）即显著超越；
3. **确定性**：跨并行度/路由方式指纹全同（现有门标准）。
